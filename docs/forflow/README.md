## 已确认的产品范围

- 首批使用者是我们团队和客户的 AI／研发团队，保留项目、任务、终端、文件、浏览器、差异审阅的专业工作方式。
- 国内产品名为 **Forflow One**。先完成国内品牌、国内／内网模型、客户域部署、消除境外服务强依赖。
- 暂无客户指定的国产软硬件／供应链替代清单，因此当前继续使用 Electron、React、Node 等工程底座；逐项记录依赖来源与可替代性。
- 模型同时支持国内 API 和客户内网；用户已明确先验证国内 API，并补充豆包、WorkBuddy、QoderWork 等 CLI 候选。本轮提供阿里云北京地域验证入口，内网路径复用相同接口合同。
- 治理建设要把数据、动作、证据、复核和整改连接到真实任务，而不是先拼装九个空页面。

## 为什么采用这个基线

本机 `/Applications/Orca.app` 为 **1.4.205**。开发基线固定到 [v1.4.205 的实际提交](https://github.com/stablyai/orca/tree/11aba8bdc5e492d3ba01fc7fe333495ace74128f)，分支 `codex/forflow-cn-v1.4.205`。同期上游 main 为 `ea02d9070486934c3ba4d21219f6ea78581366dc`，与此 tag 有 4,246 个文件差异，而且 main 的 package.json 版本显示 1.4.197，不能单靠版本号判断先后。

`~/orca` 只有工作区数据，并非源码。新源码与开发数据位于本工程；没有覆盖本机安装的 Orca，也没有迁移其账户或会话。

## 当前可用入口

在仓库根目录执行：

```sh
pnpm dev:forflow --dry-run
pnpm dev:forflow --show
pnpm build:forflow
pnpm package:forflow:mac
pnpm audit:forflow
pnpm probe:model:forflow
```

`dev:forflow` 默认后台启动，人工查看时加 `--show`。它固定 `FORFLOW_BUILD=1` 和 `cn-private`，开发数据保存在 `.forflow/dev-profile`；新工作区默认位于用户目录下的 `Forflow One/workspaces`。构建不会安装全局 `orca-dev` 链接。旧协议、RPC、文件格式中的 Orca 标识保留兼容，迁移顺序见计划。

`build:forflow` 是桌面构建。`package:forflow:mac` 另做独立身份、本机 ad-hoc 签名的 arm64 应用包，输出到本机缓存以避免同步目录污染签名。上游的 `build:mac`、`build:win`、`build:linux` 仍包含原品牌安装与更新逻辑。正式证书公证、其他平台及升级回退仍需单独验收。
