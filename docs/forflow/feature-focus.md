# 任务、并行与审阅入口收敛

## 2026-10-07 · 先明确审阅的用途

用户本轮校正：「为什么需要审阅功能，审阅是用来干嘛，达到什么效果，用户怎么认知，这些部分先想明白再做优化，而不是无谓的修改」。暂停继续调整审阅 UI；下文保留此前入口调整的依据与实现记录，但“把审阅提升为常驻主要动作”的产品价值尚未验证。

### 当前事实与错位

核对当前工作树代码后，可以确认：

- 任务页通过 `openModal('forflow-review')` 打开通用入口，没有传入当前任务、要求或产出；新建审阅从选择工作区开始，再填写要求和选择文件。
- 提交材料调用 `openWorkspaceReview`，读取来源、建立版本并记录本地敏感线索。围绕要求的模型检查位于后续 Jev 流程，需要再次选材、准备和发送。打开工作台与完成质量检查是两个动作。
- 已有来源定位、版本比较、问题采纳、处理记录和按单项要求检查的基础。当前入口尚未串起“本任务的要求与产出—检查发现—回原智能体修改—复查”的默认流程。
- 并行产出比较目前准备普通对话草稿，由用户补入两份产出。它与材料审阅并不是同一条已连通的处理流程。

因此，用户难以理解不能只归因于名称、字号或说明不够。入口承诺帮助判断交付，实际首先要求用户组织材料、学习审阅工作台，并选择检查机制。此前借鉴其他产品的任务与代码审阅顺序，不足以证明这套材料审阅应成为所有用户的主要入口。

实现依据：`ForflowTaskGuide.tsx`、`ForflowReviewDialog.tsx`、`use-workspace-review-intake.ts`、`CodexReviewStore.open`、`JevAuditPanel.tsx`、`JevDeliveryResults.tsx`、`ForflowParallelGuide.tsx`。上述判断来自源码核对，本轮未新增运行验证。

### 产品判断：帮助用户决定如何处理交付

建议将日常审阅的核心任务定义为：**围绕用户原本的要求，指出交付中影响采用的问题，并帮助用户把它改到可用。**

优先验证研发任务完成后的交付核对，再延伸到研究和文档。这个顺序沿用已有输入范围；治理用途及敏感审阅仍保留其独立需求。以下场景与排序是本轮产品建议，尚不是用户确认的新开发范围。

| 用户情境                           | 用户要做的决定                             | 产品应提供的结果                                                     |
| ---------------------------------- | ------------------------------------------ | -------------------------------------------------------------------- |
| 一个智能体完成代码、文档或研究交付 | 能采用哪些内容，还需要改什么               | 对照要求的关键遗漏或错误、具体位置、影响及修改或验证动作             |
| 多个智能体给出不同方案             | 采用哪版，保留哪些部分                     | 同一标准下影响选择的差异、各自依据和适用条件；选择后仍可检查所选交付 |
| 项目交接或治理复核                 | 本次核查了什么，问题由谁处理、处理到哪一步 | 要求、来源版本、发现与处理记录，以及按需的敏感信息和适用规则检查     |

日常交付把关、方案比较和治理复核可以复用来源与版本能力，但默认流程应分别回答上述决定。简单问答、随手草稿不必增加审阅步骤。

### 相比在聊天里说“再检查一下”，为何值得做成能力

只有在以下环节减少用户工作、改善交付判断，专门能力才有价值：

1. 沿用任务的有效要求，自动整理本次相关产出供用户确认，减少重复描述和手工搬运材料。
2. 按要求选择检查方式：程序验证可执行行为，另一智能体查找遗漏或反例，用户决定采用与否。多个智能体的意见一致不单独作为正确依据。
3. 把发现绑定到具体交付位置、依据和版本，优先呈现影响采用的少量问题，让用户能直接核对。
4. 将选中的问题带回原任务形成修改指令，更新交付后复查原问题，保留采用或不采纳的理由。

如果实际使用只是换一个模型生成泛泛评价，普通对话就足够，不应要求用户维护额外工作台。

### 用户认知与呈现原则

用户应从当前任务理解下一步：“结果出来了，我可以直接采用、检查后修改，或者与另一版比较。”主路径建议为 **交代任务 → 查看产出 → 按需检查或比较 → 采用／继续修改**。审阅跟随明确的交付物出现，不要求用户先理解审阅、台账、版本或 Jev 的分工。

结果优先回答三件事：对当前要求的判断、最值得处理的问题、下一步怎么做。依据从具体问题展开；版本和完整处理记录按需查看。不同用户不必面对相同的全部治理选项。按钮命名与视觉层级在确认实际流程后决定，本轮不先替换词语。

例如，任务要求同时支持 CSV 和 Excel，交付只包含 CSV：有用的结果应指出 Excel 支持缺失、对应要求与交付位置，并能把这一项带回任务补齐。修改后再核对 Excel 是否可用。单独显示一个分数、总体评价或“检查完成”，无法支持这次采用决定。

### 优化前的最小验证

选三份真实交付：研发功能、研究或文档、同题两版方案。固定要求和材料版本，比较用户直接阅读、普通对话检查与拟议审阅流程；记录：

- 是否发现了会影响采用且能核实的问题，是否漏掉关键问题；
- 用户花在选材、核对和决定上的时间，以及无用提示增加的工作；
- 发现能否转成具体修改，修改后能否确认原问题解决。

先检查使用者能否自行说清“什么时候用、会得到什么、下一步怎么做”，再验证完整操作。入口点击率、检查数量、模型分数或生成报告数量不作为价值成立的依据。若普通对话已经达到同样效果，优先保留轻量任务动作；若来源、版本和问题处理确实减少反复核对，再决定工作台的默认范围。

本轮仅校正用途、场景和验证方式；未改变 UI、运行逻辑或已安装版本，也未执行上述真实交付对照。

## 功能层级

- 首要：描述任务，在原对话发送与继续。
- 关键扩展：按同一目标另做方案，收集产出后准备比较草稿。
- 结果检查：查看文件或代码改动；按要求选择材料开展审阅；回到原任务继续完善。
- 按需使用：分屏、操作说明、连接来源和高级设置。

并行对比入口准备可编辑草稿，不自动复制所有上下文、不批量启动智能体；原有 Git 与文件夹执行方式保持不变。审阅入口复用原有材料读取和 Jev 流程，不扩大远程材料可读范围。

## 验收

检查新建和并行动作是否进入原有草稿；任务页及会话都能直达材料审阅；审阅返回列表和关闭窗口后原对话草稿保留；文件菜单能打开真实文件树；浅色、深色及窄窗口可读。运行结果记录于对应版本交付说明。
