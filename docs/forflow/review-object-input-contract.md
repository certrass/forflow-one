## 输入对象

| 对象 | 首批输入 | 边界 |
| --- | --- | --- |
| 对话 | 用户目标与有效约束、指定轮次的用户／助手原文、工具调用返回、相关交付物和待核实主张 | 主机／来源／会话 ID、起止轮次、时间和内容版本；选片段须明确范围 |
| 研发项目 | 目标及验收项、明确选择的关联会话、文件与变更、测试／构建回执 | 主机／工作区 ID、基线和当前版本、文件快照及证据清单；支持 Git worktree 和普通文件夹 |

业务项目后续接入需求、文档、依据与交付材料，沿用同一结构。本阶段不自动导入业务资料或调用新的分析模型。

两种对象最终都拆成审阅项：**问题及规则版本、待核实主张、相关上下文、支持／反驳证据、缺失项、来源引用和版本**。项目汇总多个审阅项，不能用项目名或自动摘要替代原文，也不能将一条“无异常”升级为项目通过。原始消息、明确指令、工具结果和派生摘要须区别标记。

身份与版本由程序确定。会话跨工作区、项目重名或关系不明时保留未归属状态，允许人工调整；不按标题相似度强行合并。Git 使用提交及未提交内容指纹，普通文件夹使用文件清单和内容指纹。

现有工作区能力已完成只读复用核对：项目采用 `Project.id`／`ProjectHostSetup`；Git 工作区采用 `Worktree.identity.key`，普通文件夹采用 `executionHostId + folderWorkspaceId`。复用已授权路径、有界文件读取和 runtime Git 状态服务。Quick Open 文件列表在 SSH 不可用时可能返回空数组，不能直接用作审计完整清单；项目读取器须先判定所属主机可读，不能落到同名本机路径。`.26` 已实现登记工作区入口、显式关联会话和文件／回执版本清单；首次使用缺持久身份的 Git 工作区须先在应用打开。当前仅本机可读；SSH/runtime/WSL 均显示尚未接入，仅读取选定文件，不扫描整库。

## 分类与判断

| 层次 | 取值示例 | 决定方式 |
| --- | --- | --- |
| 对象 | 对话、项目 | 用户入口与明确对象 ID |
| 工作类型 | 编码、调试、研究、文档、规划、工具操作；可多选或未知 | 来源元数据给出初始标签，模型可建议，用户可修正 |
| 检查类型 | 当前：执行异常、证据充分性、主张一致性；后续：适用的 176 号令事项及敏感内容使用／外发 | 版本化依据、内部制度和适用条件；执行事实与声明保存在台账供审阅引用 |
| 判断 | 支持、直接冲突、证据不足、无法判断、不适用 | 程序事实检查和模型判断分别记录；不适用须有理由 |
| 处理 | 待复核、确认问题、驳回、解决后复验 | 人工动作及新增回执 |

当前 Jev v2 的各题选项保持原样；上表是拟议的统一产品表达。每条结果都应带原文／日志／文件定位、对象版本、检查依据、缺失证据和判断来源。

退出码、文件指纹、来源是否存在、测试是否对应当前版本，优先由程序核验。Jev 用于给定上下文和明确规则下的小范围语义判断。跨多份材料推理、深度代码分析或外部事实调查需要相应分析能力，不归因于 Jev。

## 验证与实施顺序

1. **输入验证**：核对对象成员、角色、时间和版本；列出包含、排除、截断、不可读来源。每条发现可回跳原文，跨会话／主机／同名项目不串证据。
2. **分类验证**：分开标注对象归属、工作类型、检查适用性与问题标签。验证类型误判是否漏掉适用规则或错误套用规则；保留多标签、未知和人工修正。
3. **判断验证**：人工固定中文标签和分歧，冻结问题及模型版本；按完整会话／项目划分诊断集和未参与调节的保留集，防止相邻轮次、改写样本泄漏。逐类报告误报、漏报、错误放行和 unknown 覆盖率，并报告有判断时的一致率。
4. **对照验证**：先建立程序规则基线，再核对 Jev 增加的发现是否有证据。另一个模型的赞同不能单独充当正确标签，要结合人工和真实执行／原文回执。
5. **修复验证**：在新版本重新执行适用检查。旧版通过不继承到新版；问题从输入中消失不等于解决，须有回答原问题的新证据。

关键反例：启动≠完成；配置保存≠认证；旧版测试≠新版通过；单文件通过≠项目通过；预期报错／成功重试≠未解决失败；失联≠退出；引用／否定／日志指令≠事实或授权；同名项目不同根目录；删除失败返回后应显示证据不足而非通过。

当前合成保留集 10/12 全题一致，冲突预测仅 3/5 符合标签；标签仍有对象／时间语义分歧。完整对话、研发项目和业务资料的独立人工标注验收尚未完成。继续人工复核，confidence 不作自动确认依据；原始结果见 [验证回执](jev-review-validation-20260921.md)。
